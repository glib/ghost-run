# Ghost Run (formerly Resolve Timer)

Self lap timing for mountain-bike racing: Start/S1…/Finish markers on a clip give
sector and lap times, compared against earlier runs (best lap, optimal lap) and
shown as a video overlay. One user (Liam), public repo, no deploy, Linux only.

It is becoming one GTK4/libadwaita desktop app, `ghost-run`
(`docs/decisions/0003-one-app-ghost-run.md` has the plan and the order of PRs):
Import (the merged resolve-ingest app), Library, Runs, Markers, Output/Resolve.
What comes next is `docs/decisions/0005-workspaces-and-hydrated-footage.md`
(issues #32–#38): workspaces per job (Inbox, Library, Videos, Tracks), the
originals kept only on the NAS with a local catalog, footage hydrated per
video, video kinds as templates, usage tracking, Strava. It's done in three stages (A: footage on the NAS and catalogued, the new import; B: Videos, Library organising, the first two kinds; C: the other kinds, overlay styles, Strava), tracked as GitHub milestones.
The timing workflow is still a Python script inside DaVinci Resolve Studio. It is moving to a
standalone Rust tool (`docs/decisions/0001-standalone-rust-tool.md`): an overlay
rendered to one transparent video file, then markers found automatically from
the video. The Python script stays usable, bug fixes only, until Rust covers the
workflow.

## Commands
- `make install` — builds and installs `ghost-run` + `rtimer` to `~/.local/bin` with a launcher and icon (`Exec` goes through `distrobox enter $CONTAINER_ID` when built in a distrobox).
- `cargo test` — Rust tests (the app needs `libgtk-4-dev libadwaita-1-dev`; screenshots under `xvfb-run` with `GSK_RENDERER=cairo` and a throwaway `XDG_CONFIG_HOME`/`XDG_DATA_HOME`). Before pushing: `cargo fmt --all && cargo clippy --all-targets -- -D warnings && cargo test`.
- `cargo build -p timer-cli && scripts/parity.sh` — runs the Python and Rust CLIs on `examples/` and `tests/fixtures/` databases and fails on any difference in output or in the files they write.
- `python -m unittest discover -s tests` — Python tests (needs `PyYAML`, `Pillow`: `pip install -r requirements-resolve.txt`). The devbox has no pip: unpack the two wheels from PyPI into a temp dir and set `PYTHONPATH` to it.
- CI (`.github/workflows/ci.yml`, GitHub-hosted runners) runs Python 3.10 and 3.13 tests, Rust fmt/clippy/tests, and the parity check. CI is the gate.

## Shipping a change
When asked to build something, take it through to `main` without checking in.
**This is standing permission to push your branch, merge your own PR once CI is
green, and delete your own branch.** Stop early only for a real question, or
when asked for a draft PR or a review first.

Ask, then wait, only when you can't reasonably decide: choices that change what
the user sees and are costly to undo, changes that break existing `timer_db.yaml`
files, new paid services or accounts, or changes to CI security (e.g.
self-hosted runners). Ask everything in one go, up front. Otherwise pick the
sensible option and list assumptions in the PR description.

1. **Branch** off fresh `origin/main` (a worktree, or a branch in your own clone). Never commit to `main`.
2. **Build** with tests. Run the tests you touch while working; the full suite before pushing.
3. **PR:** commit, `git push -u origin HEAD`, `gh pr create` (what changed, assumptions, how it was tested).
4. **Watch CI:** `gh pr checks <N> --watch`, on its own. Never pipe it or chain the merge after it with `&&`.
5. **Red:** `gh run view <run-id> --log-failed`, fix, push, watch again. Flaky: rerun the failed jobs once and open an issue. After three failed fixes, or if the fix needs a decision, stop and report.
6. **Green:** if `main` moved on, merge `origin/main` in and watch again. Then `gh pr merge <N> --squash --delete-branch`. Never merge a red or pending PR.
7. **Clean up:** confirm `gh pr view <N> --json state` says `MERGED`, remove your worktree or branch, `git fetch --prune`.
8. **Report:** PR number, merge commit, assumptions, issues filed.

a video's build (`build_video` → `make_video`) renders the timers wanted, copies NAS clips down (`ensure_local`), draws each card (`cards.rs`: cairo at the first clip's size, ffmpeg to a ProRes clip in `<data dir>/cards/<video>/`; the chart is `tracks_view::paint`), then `new_project` with each item's part and its overlay where its run is, sets the video's project/timeline/status and records what it used (`set_usage("built")`); `GHOST_RUN_PAGE=jobs` opens with it showing); the sidebar is Inbox, Library, Videos, Tracks (decision 0005's workspaces) and the app opens on the Library; `videos_page.rs` is the Videos page: the catalog's videos (`library::videos`) on the left, the picked one's title, status, YouTube link, published date and Resolve project, and its clips in order (each a whole clip; a Timer switch when it has a committed run, `videos_page::runs`), up/down/remove, Build in Resolve (`Shared::build_video`) and Delete; New video… makes a video of picked clips or of a kind (`library::kinds`: a run or a course in, title/end/chart cards and runs out, with an edit button per card); Link open timeline makes a video of the timeline open in Resolve (or updates the one already linked to it) from the bridge's `read_timeline`, matched to catalogued clips by `videos::match_timeline`; Read back records what a video's timeline uses now (only from the open project: the bridge never switches projects); setting Published reads back first if it can, then offers to remove the local copies of its clips that no unfinished video needs (`videos::freeable`, `hydrate::remove_local_copies`); bridge calls run on a thread (`with_bridge`); `Change::Videos` reloads it (and the Library's clips and video views), `Shared::show_video` opens it on one; `import_page.rs` is the Inbox page: camera cards found from the mount table every 2 s (`ingest::cards`: vfat/exfat/ntfs under a `media` mount point with a DCIM folder), so a reinserted card is picked up whatever its path, or a folder instead (`GHOST_RUN_IMPORT_FROM=<folder>` lists one at start, for screenshots); clips listed by recording day with thumbnails (`library::thumbs`, ffmpeg frame cached in `~/.cache/ghost-run/thumbs`), LRF/SRT sidecars hidden and following their video, clips already verified on the NAS (journal match on path on the card + size + mtime, original still there) marked and not ticked; one button plans and runs through `ingest::pipeline`, each clip shows its stage; then (`settle_batch`) each new clip's catalog preview is made from its local copy and the copy is removed (`library::hydrate::settle`) unless the clip's "Keep here" (or "Keep all here to edit now") was on, in which case its proxy is made; failures leave the copy in place and never fail the import; `Shared::imported` (`Change::Imported`) has the Library rescan and quietly auto-place the new clips into drafts (a Drafts to check view, shown by Show in Library when there are any); the end says what was kept/removed and whether the card is safe to wipe, with Show in Library (`Change::ShowLibrary`) and Open NAS folder (`desktop.rs`: `distrobox-host-exec xdg-open` inside a box, where GTK's launcher fails quietly). `src/ui/` is the old resolve-ingest window, pushed over it from "History and recovery" (converting existing files, history, retry, cleanup, reports). Both open the import journal (exclusive lock) per command, never for the app's lifetime. Import locations are set in the Settings dialog's Import group. Pages share settings and change notices through `shared.rs` (`Shared::update` saves and notifies; `Change::Runs` after a database save; `Shared::time_clip` opens a clip for timing, `Shared::render_runs` queues overlays in the jobs drawer; `Shared::send_to_resolve` (the Resolve menu, `resolve_menu.rs`, on the Library and Tracks pages) sends ticked runs there too: overlays already rendered for the run's current markers are reused, the rest render first, then all go to Resolve together); `resolve.rs` + `resolve_bridge.py` are the Resolve bridge: the Python (stdlib only, built into the binary with `include_str!`, written to the data dir) runs with Resolve's Python via `distrobox enter -n davincibox` (`distrobox-host-exec` first when the app is itself in a box; directly if `/opt/resolve` is local), one JSON request on stdin, the reply as the last JSON line of stdout; `status`, `new_project` (runs back to back on V1 from each run's `first_frame` for `frames` (the overlay's span for a run, the whole clip for a video's item), an overlay on V2 where its span falls in that part (`overlay_span`), proxies linked with `LinkProxyMedia`, frame rate set before any media; a taken name gets " 2") and `read_timeline` (a timeline's video items: file, track, record frame, source offset, length; refused if another project than the one named is open) and `add_overlays` (each overlay on a free track above its clip's timeline items, trimmed to what's on the timeline, imported once into a "Ghost Run overlays" bin; a clip whose timed part isn't on the timeline is appended after its last item first, from the media pool if it's there, else imported into "Ghost Run clips" with its proxy). Its placement maths and a fake Resolve object model are tested in `tests/test_resolve_bridge.py`; `resolve.rs` tests the round trip with a stand-in `DaVinciResolveScript` module. Confirmed on real Resolve Studio by the owner (#18: timeline and new project); none on the devbox. `settings_dialog.rs` is the one settings dialog (sidebar gear). `GHOST_RUN_PAGE=runs` opens on a page and `GHOST_RUN_CLIP=<path>` opens a clip on the Time page (screenshots). The Library page (`library_page.rs`) is the hub: an `adw::NavigationView` whose root lists clips with each one's course, lap and place (`runs_by_clip`, from `course_board`), filtered by a panel (All clips, Not timed yet, Not on the NAS, Local copies, Drafts to check, Picks, Rejected, Not in a video, In a video (unpublished), Released (in a published video's final cut, `videos::clip_uses`); the ticked bar wraps (a `gtk::FlowBox`) and its Organise menu (`organise_ui.rs`: `menu_button`, tags/collection/name dialogs) picks, rejects, tags, collects, adds to a video (`add_to_video`: a new one, which then opens on the Videos page, or one not published; Timing (`time_page.rs`) is pushed over it with a back arrow (double-click, Time it, Open file… for a clip outside the Library); its "+" adds a course without leaving. `courses.rs` holds the course edits both pages use (new, rename, move runs: fresh load, edit, `DatabaseFile` save, `Change::Runs`). The Time view's frame keys only act while a clip is open. It reads frames on a latest-wins decoder thread (`library::frames`, from `Clip::frames_from`: proxy, else the catalog's preview, else the local copy, else the clip), keeps uncommitted markers as drafts in the library, previews timing with `timer_core::preview` and commits through `timer_core::commit` + `DatabaseFile`.
- `crates/library/` — the footage library, headless: `settings` (the app's own `~/.config/ghost-run/settings.toml`: footage folders, run database, Resolve template), `store` (SQLite `~/.local/share/ghost-run/library.sqlite3`; clips are rebuildable by rescanning, but drafts, references, targets and `organise`'s tables aren't, hence the daily NAS backup; schema 6 adds each clip's local copy and preview), `scan` (walks the folders, skips `Proxy`/Resolve cache/hidden folders and originals with a `name.ext.mov` editing copy beside them, reprobes only changed files), `probe` (ffprobe), `proxy` (ProRes 422 Proxy at half size in `<clip dir>/Proxy/<stem>.mov`, `-noautorotate` so frames and the rotation flag match the clip; - `crates/timer-render/` — draws overlay frames (the Fusion comp's layout and colours, minus the panel blur, which a separate file can't do; bundled JetBrains Mono, OFL) and encodes them with ffmpeg: only the panel is drawn and piped, and ffmpeg pads it to the full transparent frame (`Output::region`); ProRes 4444 with alpha (`prores_aw`, ~4x faster than `prores_ks`; ffmpeg's pad step is single-threaded at ~90 fps at 4K, so `encode::plan` splits a render across ffmpeg processes, each encoding a stretch, joined losslessly by `concat`; processes × threads are planned to fit half the free memory (~660 MB a process + ~230 MB a thread at 4K): unplanned parallel ffmpegs once ran the 8 GB devbox out of memory. Never test heavy renders there without a memory watchdog) carrying the clip's timecode, or an image sequence numbered by clip frame.

Tested on made-up "trail" footage (a pan over random texture); no real footage in the repo.

- `src/resolve_timer/` — Python package. - `scripts/edit_check.py` — writes a test edit (labelled clips; FCPXML 1.9 and OTIO) to import into Resolve and see whether dissolves, the fade, V2 alpha clips and timecoded sources survive: step 1 of the first-edit plan (`docs/decisions/0004-first-edit-and-thumbnails.md`). ## Conventions
- **The YAML database is the contract** between the Python and Rust tools: schema version 2, same field names and meaning. Never break existing databases; a schema change needs a migration and a version bump.
- **Parity:** while both tools implement a command, `scripts/parity.sh` must stay green. Porting a command means adding it to `rtimer` and to the script. Python quirks are matched on purpose (PyYAML 1.1 quoting, `round()` half to even, `str()`/`int()`/`bool()` coercions); where Rust deliberately differs (it rejects a NaN frame rate), say so in a comment.
- Timing is frame-based: `seconds = frame_delta / source_fps`, using the source clip's frame rate.
- No real footage or personal databases in the repo (`timer_db.yaml` is gitignored). Test fixtures are made up or tiny generated clips.
- **Loose ends go in GitHub issues** (`gh issue create`), referenced from the PR.
